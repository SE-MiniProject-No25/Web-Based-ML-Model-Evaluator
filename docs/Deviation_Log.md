# Deviation Log
## Web-Based ML Model Evaluator

Every place where what was built, or how it was built, differs from the plan in the Deliverable 1 documents ([SRS](../deliverable-1/01_SRS.md), [Architecture and Design](../deliverable-1/03_Architecture_and_Design.md), [Test Plan](../deliverable-1/02_Test_Plan.md)) and the [Product Backlog](../planning/Product_Backlog.md) and [Sprint Plan](../planning/Sprint_Plan.md). Each entry says what the plan said, what was built, why, what it affects, and where the change happened. Each affected document links back to its entries here.

Design deviations (D) change *what the system does or how it is built*; process deviations (P) change *how the team worked*. Nothing here removes a requirement: every FR, NFR and SEC requirement is still met (see the [System Validation Report](System_Validation_Report.md)).

## 1. Design deviations

| ID | The plan said | What was built | Why | Impact | Where |
|---|---|---|---|---|---|
| D-01 | SAD §3 lists the components (API Controller, Validation, Evaluation, Metrics, Result Service, Temporary Storage, Security/Policy) but not how the code is laid out | One Python package per component under `backend/app/` (`api`, `validation`, `evaluation`, `metrics`, `results`, `storage`, `security`), plus shared `errors.py` and `config.py`. The allowed imports between them are checked by `tests/test_architecture.py` on every pull request | Makes the component boundaries visible in the code and testable (NFR-09) | None on behaviour. README "Code Map" maps each folder to its SAD component | EN-01, EN-04 (#31, #33) |
| D-02 | SAD §9 (upload validation) checks that the model is a valid model before evaluation, without saying where it is loaded | The model is opened in a **separate child process** (`model_inspector.py`) *before* the `202`, with a sanitized environment and a timeout; the evaluation itself runs in another child process (`worker.py`). The server never unpickles a model | Loading a pickle runs code inside it; doing that in the server process would let an uploaded model take over the server | Validation costs a process start and a scikit-learn import before the `202` (about 1.6 s), which put the 2-second target (NFR-02) at risk (DEF-05). Reduced in Sprint 3 by D-11 | US-07 (#39), EN-06 (#34), #44 |
| D-03 | SAD §6.2 "apply execution/resource limits"; the Sprint Plan calls for "an isolated, time-limited process" | **Process isolation, not a container sandbox**: a child process with a sanitized environment (no server secrets), a wall-clock limit and a memory limit. A malicious model can still run code with the server user's rights | A container or VM was out of scope for a one-month student project | Documented as a known limitation in the README and as DEF-06 (accepted) | US-04 (#49) |

| D-05 | SRS NFR-07 and SEC-06: authentication "if enabled by the deployment configuration", mechanism not specified | **Optional API key**, off by default: `MLEVAL_AUTH_ENABLED=true` and `MLEVAL_API_KEY`; the key is sent as `X-API-Key` or `Authorization: Bearer`; `401 UNAUTHENTICATED` without it; `/api/health` stays open. | D-06 | SAD §5 step 10 and SEC-07: artifacts removed "according to retention policy" | Sprint 2: expired uploads were removed only when a new evaluation was submitted, and the sweep did not protect files still in use (DEF-02, DEF-10). Sprint 3: swept at start-up, every `MLEVAL_CLEANUP_INTERVAL_SECONDS` (300 s) and after each submission, and the files of pending or running evaluations are never deleted | The lazy version was the simplest to build in Sprint 2; Part-3 testing showed its two gaps | TC-18 in the Test Plan describes the final behaviour | US-10 (#57), TEST-05 (#89) |
| D-07 | Sprint Plan risk "model loading must happen in an isolated, time-limited process" and SEC-04 "resource limits" | Sprint 2: time limit everywhere, memory limit on Linux and macOS only (DEF-04). | D-09 | Sprint Plan §6: result download as JSON, "CSV can be added if time allows" | JSON only | Time | FR-15 ("a structured format") is met by JSON | US-03 (#48), US-17 (#62) |

## 3. One-page summary for the demo

**What changed in the design (and why it is allowed):**
- **Same requirements, same API.** The three endpoints, their fields and the 13 error codes of SAD §10–11 are unchanged. Three extra codes cover errors outside the workflow (unknown URL, wrong method, unexpected crash), so every error has one format (D-04).
- **Models are never opened in the server.** They are opened in a child process, both to check them (before the `202`) and to evaluate them, with time and memory limits on Linux, macOS and Windows. It is process isolation, not a container, and that is stated as a limitation (D-02, D-03, D-07).
- **Authentication is an optional API key** (the SRS left the mechanism open) (D-05).
- **Results live in memory** for the session, as FR-18 asks; download is JSON (D-08, D-09).
- **Part-3 testing changed four things:**
  - Retention runs on a timer and never deletes files in use (D-06).
  - Text class labels work (D-10).
  - Common CSV variations are handled or refused clearly (D-12, D-13).
  - Acknowledgement is about 0.2 s instead of 1.7 s (D-11).

**What changed in the process:**
- The two one-week sprints overran. 26 of 79 points were in by the planned end, so a **Sprint 3 (3–11 Nov)** finished the spill-over and did the Part-3 testing (P-01, P-02).
- Akash's backlog items were tracked under test-story issue numbers (P-03).
- Most pull requests were checked and merged by the team lead without a formal GitHub review. Branch protection with a required review is on after the freeze (P-04).
